Vela is a compile-time utility-class system for `roblox-ts` React. You write Tailwind-shaped class names on Roblox host elements and on your own components, and a TypeScript transformer rewrites them into real Roblox properties and helper instances before roblox-ts emits Luau.

Nothing about Vela is a runtime library you render. It is a transformer you register in `tsconfig.json`, plus a config file it reads from disk. This page gets both in place.

## Install the package

<PackageInstall packageName="vela-rbxts" />

`vela-rbxts` expects the ordinary roblox-ts React stack alongside it. Install those yourself if the project does not already have them.

<PackageInstall packageName="@rbxts/react @rbxts/react-roblox @rbxts/services" />

`@rbxts/react` and `@rbxts/services` matter beyond your own imports: when Vela takes its runtime path it inlines a helper module into your output that imports `React` from `@rbxts/react` and `{ UserInputService, Workspace }` from `@rbxts/services`. Both must resolve in the built place even if you never import them by hand. `@rbxts/react-roblox` is what you need to mount a tree at all.

<PackageInstall
  dev
  packageName="roblox-ts typescript@5.9.3 @rbxts/compiler-types @rbxts/types"
/>

<Callout title="Pin TypeScript — the current release does not work">
The version is pinned in that command for a reason. Vela's host adapter resolves `typescript` from
**your** install and calls into its API, and TypeScript 7 moved enough of it that the call fails.
Installing plain `typescript` today gets you 7.x and a build that dies on the first file:

```text title="rbxtsc output with typescript@7"
src/client/Panel.tsx:1:1 - error TS89000: [@vela-rbxts/rbxtsc-host] compiler-invocation-failed: Cannot read properties of undefined (reading 'Latest')
```

`5.9.3` is what the Vela repo pins and tests against; `6.x` also builds. Nothing enforces this —
no package in the repo declares a `peerDependency`, and the only `engines` field anywhere is the VS
Code extension's `vscode: ^1.90.0` — so your package manager will not warn you, and the error you
get names neither TypeScript nor a version.

The rest of what Vela is developed against: **Node 24** in CI, **roblox-ts `^3.0.0`**,
`@rbxts/compiler-types ^3.0.0-types.0`, `@rbxts/types ^1.0.935`, `@rbxts/react ^17.3.7-ts.1`, and
`@rbxts/services ^1.6.0`.
</Callout>

## Register the transformer

Vela runs as a roblox-ts transformer plugin. Add one entry to `compilerOptions.plugins` in your existing `tsconfig.json`:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "plugins": [{ "transform": "vela-rbxts/transformer" }]
  }
}
```

That is the entire tsconfig change. Everything else in the file stays as your roblox-ts project already has it — Vela requires no compiler option of its own, and if the project builds today it will keep building. If you do not have a project yet, start from [roblox-ts's quick start](https://roblox-ts.com/docs/quick-start) and come back here.

`vela-rbxts/transformer` is a separate export from the package root. The root export (`vela-rbxts`) gives you `defineConfig` and types; the `/transformer` subpath is the callable roblox-ts consumes. Do not swap one for the other.

The plugin entry object is also where transformer options go — file-filter toggles, a diagnostic code base, a project root. The defaults are what you want to start with; the [configuration reference](/vela-rbxts/reference/config/) covers the rest.

## Add `vela.config.ts`

Vela looks for `vela.config.ts` or `vela.config.json` (the `.ts` form wins when both exist), walking up from the directory of each source file until it finds one or hits the filesystem root. There are no `.js`, `.mjs` or `.cjs` variants and no `package.json` key. If nothing is found, Vela uses its built-in default theme, which already contains 28 color families, the radius scale, and the spacing fallback.

<Callout title="Put it next to tsconfig.json, not inside src">
Vela loads this file itself, with Node — it is build tooling, not game code. Keep it at the project
root, **outside** `rootDir`. Dropped into `src/`, roblox-ts sweeps it up with the rest of your
sources and fails the build outright:

```text title="rbxtsc output"
src/vela.config.ts:1:30 - error TS roblox-ts: You cannot use modules directly under node_modules.

1 import { defineConfig } from "vela-rbxts";
                               ~~~~~~~~~~~~
```

Note that this is the opposite of the `.d.ts` file below, which *must* live inside `rootDir`.

One wrinkle at the root: a roblox-ts `tsconfig.json` includes only `src`, so a typed-ESLint setup
will report `vela.config.ts` as a file not included in the project. Widening `include` would hand
the file back to roblox-ts, so the fix is either an ESLint override for that one path or the JSON
form, `vela.config.json`, which no TypeScript tool tries to own.
</Callout>

The minimum useful file accepts the defaults wholesale:

```ts title="vela.config.ts"
import { defineConfig } from "vela-rbxts";

export default defineConfig();
```

When you do want your own values, put them under `theme.extend`. Every value is an **expression string written in the roblox-ts dialect**, not a color object or a number:

```ts title="vela.config.ts"
import { defineConfig } from "vela-rbxts";

export default defineConfig({
  theme: {
    extend: {
      colors: {
        brand: {
          500: "Color3.fromRGB(59, 130, 246)",
          700: "Color3.fromRGB(29, 78, 216)",
        },
      },
      radius: {
        panel: "new UDim(0, 10)",
      },
    },
  },
});
```

<Callout title="Use theme.extend, not top-level theme.colors">
A top-level `theme.colors` **replaces the entire color registry** and, critically, causes `theme.extend.colors` to be discarded silently — no error, no warning. Setting both means only the top-level scale survives, every built-in palette disappears, and your `extend` colors never resolve. This differs from real Tailwind, where `extend` is layered on top. The same replace-wholesale rule applies to `theme.radius` and `theme.spacing`. Unless you genuinely want to throw away every default, add colors through `theme.extend.colors` alone.
</Callout>

Full details on merge behavior and the shipped defaults are in the [theming guide](/vela-rbxts/guides/theming/).

## Declare the `className` prop

Roblox host elements have no `className` prop in `@rbxts/types`. Vela adds one by augmenting `React.Attributes` globally, and that augmentation only takes effect if the package is imported for its side effect somewhere in your program. Create a declaration file to do that once:

```ts title="src/vela-env.d.ts"
import "vela-rbxts";
```

That single import pulls in `declare global { namespace React { interface Attributes { className?: ClassValue } } }`. Without it, every `className` you write is a type error, even though the transformer would still have processed it.

Keep the file inside `rootDir` so TypeScript picks it up with the rest of your sources.

<Callout title="Do not name the file src/vela-rbxts.d.ts">
A roblox-ts project sets `baseUrl` to `src`, and TypeScript tries `baseUrl` before `node_modules` for a bare specifier. Under that name, `import "vela-rbxts"` resolves to the declaration file itself rather than the package, so the augmentation never loads and `className` stays a type error — with no diagnostic pointing at the cause. Any other name works.
</Callout>

## Build and serve

There is no Vela-specific build step. Compile with roblox-ts as usual:

```bash title="Build"
npx rbxtsc
```

Then sync `out/` into Studio with Rojo the same way you already do:

```bash title="Serve"
rojo serve
```

You do not need a Rojo mapping for Vela, and there is no Vela runtime package to place in the DataModel. Everything Vela produces is either an ordinary Roblox property, a helper instance emitted as a JSX child, or — on the runtime path — a helper module inlined directly into the same output file. The only things that must exist in your place tree are `@rbxts/react` and `@rbxts/services`, which your existing `node_modules` → `ReplicatedStorage` mapping already covers.

## Check that it actually took

Two of the three ways this setup can fail are silent, so spend one build proving it worked. Put a
deliberately broken class on any `.tsx` element:

```tsx title="src/client/Smoke.tsx"
<frame className="bg-nope-500 p-4" />
```

Build, and read the output. You are looking for exactly this — a roblox-ts warning, numbered from
the diagnostic code base, with the offending token underlined:

```text title="rbxtsc output"
src/client/Smoke.tsx:4:28 - warning TS89000: [@vela-rbxts/compiler] unknown-theme-key: Unknown theme key "nope-500" for background color utility in className literal.

4   return <frame className="bg-nope-500 p-4" />;
                            ~~~~~~~~~~~
```

- **You get the warning.** Everything is wired: the plugin is loading, the compiler is running, and
  diagnostics are reaching you. Delete the file.
- **No warning, and `className` is a type error in your editor.** The ambient declaration is not
  loading — check the `.d.ts` file exists inside `rootDir` and is not named `src/vela-rbxts.d.ts`.
- **No warning, and `className` type-checks fine.** Either the transformer is not running (check the
  `plugins` entry spells the `/transformer` subpath, and that the file ends in `.tsx`), or your
  roblox-ts version does not expose `context.addDiagnostic` and is discarding every Vela warning.
  The second case is the dangerous one — it makes broken classes look clean forever — so upgrade
  roblox-ts rather than living with it.

Then check the emitted file. `p-4` should have become a `<uipadding>` child and the `className`
attribute should be gone entirely; if the attribute survived verbatim, the element was skipped.
