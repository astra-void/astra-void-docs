Vela is a compile-time utility-class system for `roblox-ts` UI — React by default, and [Vide](https://centau.github.io/vide/) when the project says so. You write Tailwind-shaped class names on Roblox host elements and on your own components, and Vela rewrites them into real Roblox properties and helper instances before roblox-ts emits Luau.

It is a compiler over your `.tsx` files, not a component library you render. **Where that compiler runs is yours to pick** — as a plugin inside `rbxtsc`, or as a command that runs before it. This page installs the packages, sets up whichever you choose, and gets the type declaration in place.

## Install the packages

<PackageInstall packageName="vela-rbxts" />

Then the ordinary roblox-ts stack, which Vela does not bring for you. Install the UI library you
actually write JSX with — React:

<PackageInstall packageName="@rbxts/react @rbxts/react-roblox @rbxts/services" />

…or [Vide](https://centau.github.io/vide/), which needs no Vela config of its own — the target is read off the `jsxFactory` your `tsconfig.json` already sets, see [the Vide guide](/vela-rbxts/guides/vide/):

<PackageInstall packageName="@rbxts/vide @rbxts/services" />

<PackageInstall
  dev
  packageName="roblox-ts typescript@5.9.3 @rbxts/compiler-types @rbxts/types"
/>

The `typescript@5.9.3` pin is deliberate: Vela calls into **your** TypeScript install, and 7.x fails
on the first file. Nothing enforces the pin, so this is on you.

<Callout title="pnpm needs `nodeLinker: hoisted`">
Vela's runtime reaches your place *transitively*, and pnpm's default isolated linker does not put a
transitive dependency where roblox-ts and Rojo look. Set the linker once, at the workspace root:

```yaml title="pnpm-workspace.yaml"
nodeLinker: hoisted
```

npm and Yarn hoist by default and need nothing.
</Callout>

<Details title="Why the linker matters, and why a nested .npmrc will not do">
Both roblox-ts and Rojo resolve `@rbxts/*` by walking real directories, and under pnpm's default
layout `node_modules/@rbxts/vela-runtime` simply does not exist — the package is real, but it lives
inside `node_modules/.pnpm`.

Most roblox-ts projects have `nodeLinker: hoisted` already, for the same reason and not because of
Vela. A nested `.npmrc` will not do it — pnpm reads `nodeLinker` only from the workspace root.
</Details>

<Details title="What the TypeScript pin protects you from, and the rest of the version matrix">
Vela's host adapter resolves `typescript` from **your** install and calls into its API, and
TypeScript 7 moved enough of it that the call fails. Installing plain `typescript` today gets you 7.x
and a build that dies on the first file:

```text title="rbxtsc output with typescript@7"
src/client/Panel.tsx:1:1 - error TS89000: [@vela-rbxts/rbxtsc-host] compiler-invocation-failed: Cannot read properties of undefined (reading 'Latest')
```

`5.9.3` is what the Vela repo pins and tests against; `6.x` also builds. Nothing enforces this — no
package in the repo declares a `peerDependency`, and the only `engines` field anywhere is the VS Code
extension's `vscode: ^1.91.0` — so your package manager will not warn you, and the error you get names
neither TypeScript nor a version.

The rest of what Vela is developed against: **Node 24** in CI, **roblox-ts `^3.0.0`**,
`@rbxts/compiler-types ^3.0.0-types.0`, `@rbxts/types ^1.0.935`, `@rbxts/react ^17.3.7-ts.1`, and
`@rbxts/services ^1.6.0`.
</Details>

<Details title="Why no runtime host appears in those commands">
What Vela emits for an element it could not settle at compile time is an import of a **runtime host** —
`@rbxts/vela-runtime` for React, `@rbxts/vela-runtime-vide` for Vide. Both ship as dependencies of
`vela-rbxts`, so neither appears in the commands above and neither is yours to keep in sync.

Each host declares *its* UI library as an optional peer, and that is what keeps the split honest:
Rojo maps the whole `node_modules/@rbxts` directory into the place, so `@rbxts/react` in a Vide
project would be React shipping to every player of a game that never renders it. It does not, because
nothing pulls it in. The host you do not emit for is one inert ModuleScript that no module imports.

`@rbxts/services` matters beyond your own imports for the same reason: the host reads
`{ UserInputService, Workspace }` from it to resolve viewport, input mode and rem, so it must resolve
in the built place even if you never import it by hand. `@rbxts/react-roblox` is what you need to
mount a React tree at all; Vide mounts itself.
</Details>

## Choose how Vela runs

There are two ways to run it, and they are the same compiler either way. **The transformer** registers
a plugin so the lowering happens inside `rbxtsc`. **The CLI** lowers your sources into a second tree
first, and `rbxtsc` then compiles ordinary TSX with no plugin at all.

Neither is a lesser mode. They differ in where the work sits in your build, and that decides which one
fits:

| | Transformer | CLI |
|---|---|---|
| Setup | One `tsconfig.json` plugin entry | `rootDir`/`include` point at the generated tree |
| Build command | `rbxtsc` | `vela build && rbxtsc` |
| Watch | `rbxtsc -w` | `vela watch` beside `rbxtsc -w` |
| Sources `rbxtsc` sees | Yours | The generated mirror |
| Lowered output | Never written to disk | A reviewable tree you can read and diff |
| Needs a plugin-capable toolchain | Yes | No |
| Processes to keep running | One | Two |
| Available since | 0.1.0 | 0.11.0 |

Pick the transformer when `rbxtsc` is your build and you want one moving part. Pick the CLI when a
plugin is not an option — a pinned toolchain, a build system that drives `tsc` itself — or when you
positively want the lowered sources as an artifact to inspect in review or in CI.

Everything after this section is shared: the config file, the type declaration, and the smoke test all
work the same on both.

### Track A — the transformer

Add one entry to `compilerOptions.plugins` in your existing `tsconfig.json`:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "plugins": [{ "transform": "vela-rbxts/transformer" }]
  }
}
```

That is the entire tsconfig change. Everything else stays as your roblox-ts project already has it — Vela requires no compiler option of its own, and if the project builds today it will keep building. If you do not have a project yet, start from [roblox-ts's quick start](https://roblox-ts.com/docs/quick-start) and come back here.

<Details title="Why the entry names a /transformer subpath, and what else goes in it">
`vela-rbxts/transformer` is a separate export from the package root. The root export (`vela-rbxts`)
gives you `defineConfig` and types; the `/transformer` subpath is the callable roblox-ts consumes. Do
not swap one for the other.

The plugin entry object is also where transformer options go — file-filter toggles, a diagnostic code
base, a project root. The defaults are what you want to start with; the
[configuration reference](/vela-rbxts/reference/config/) covers the rest.
</Details>

### Track B — the CLI

Point `rbxtsc` at the tree the CLI generates, and register no plugin:

```json title="tsconfig.json"
{
  "compilerOptions": {
    "rootDir": ".vela/src",
    "baseUrl": ".vela/src",
    "outDir": "out"
  },
  "include": [".vela/src"]
}
```

`vela build` mirrors `src` into `.vela/src`, transforming the `.tsx` files that use `className` and
copying everything else through byte for byte. It writes a `.gitignore` beside the tree, so nothing
generated lands in version control:

```bash title="Build"
npx vela build && npx rbxtsc -p tsconfig.json
```

If a plugin entry is still registered, or `rootDir` still points at `src`, `vela build` says so on
every run rather than letting the two paths quietly duplicate each other. The
[CLI reference](/vela-rbxts/reference/cli/) has every flag, the watch behavior, and the exit codes.

<Details title="Edit src, never the generated tree">
On track B the mirror is a build output. An edit inside `.vela/src` survives exactly until the next
run touches that file, and nothing warns you when it disappears. Your editor and `tsc --noEmit` will
point at the generated tree too, since that is what `rootDir` names — the language server still reads
your real sources, so completions and hover on `className` are unaffected.
</Details>

## Add `vela.config.ts`

Optional. With no config file at all, Vela uses its built-in default theme — 28 color families, the
radius scale, the spacing fallback — and infers the framework from your `tsconfig.json`. Add the file
when you want your own theme values:

```ts title="vela.config.ts"
import { defineConfig } from "vela-rbxts";

export default defineConfig({
  theme: {
    extend: {
      colors: {
        brand: {
          500: "Color3.fromRGB(59, 130, 246)",
          700: "Color3.fromRGB(29, 78, 216)",
        },
      },
      radius: {
        panel: "new UDim(0, 10)",
      },
    },
  },
});
```

Two things to get right: every value is an **expression string written in the roblox-ts dialect**, not
a color object or a number — and it goes under `theme.extend`, because a top-level `theme.colors`
replaces the entire registry *and* discards `theme.extend.colors` silently. Full merge behavior is in
the [theming guide](/vela-rbxts/guides/theming/).

<Details title="Where the file goes, and where Vela looks for it">
Vela looks for `vela.config.ts` or `vela.config.json` (the `.ts` form wins when both exist), walking
up from the directory of each source file until it finds one or hits the filesystem root. There are no
`.js`, `.mjs` or `.cjs` variants and no `package.json` key.

Keep it at the project root, **outside** `rootDir` — Vela loads it itself, with Node, so it is build
tooling rather than game code. Dropped into `src/`, roblox-ts sweeps it up with the rest of your
sources and fails the build outright:

```text title="rbxtsc output"
src/vela.config.ts:1:30 - error TS roblox-ts: You cannot use modules directly under node_modules.

1 import { defineConfig } from "vela-rbxts";
                               ~~~~~~~~~~~~
```

Note that this is the opposite of the `.d.ts` file below, which *must* live inside `rootDir`.

One wrinkle at the root: a roblox-ts `tsconfig.json` includes only `src`, so a typed-ESLint setup
will report `vela.config.ts` as a file not included in the project. Widening `include` would hand
the file back to roblox-ts, so the fix is either an ESLint override for that one path or the JSON
form, `vela.config.json`, which no TypeScript tool tries to own.
</Details>

## Declare the `className` prop

Roblox host elements have no `className` prop in `@rbxts/types`. Vela adds one by augmenting `React.Attributes` globally, and that augmentation only takes effect if the package is imported for its side effect somewhere in your program. Create a declaration file to do that once:

```ts title="src/vela-env.d.ts"
import "vela-rbxts";
```

Without it, every `className` you write is a type error, even though Vela would still have processed
it. Keep the file inside `src` so TypeScript picks it up with the rest of your sources; on track B the
CLI copies `.d.ts` files through unchanged, so it arrives inside the generated tree too.

<Callout title="Do not name the file src/vela-rbxts.d.ts">
A roblox-ts project sets `baseUrl` to `src`, and TypeScript tries `baseUrl` before `node_modules` for a bare specifier. Under that name, `import "vela-rbxts"` resolves to the declaration file itself rather than the package, so the augmentation never loads and `className` stays a type error — with no diagnostic pointing at the cause. Any other name works.
</Callout>

## Install the language server

Vela ships a language server, `vela-rbxts-lsp`, built from the same compiler crate the build uses —
so what the editor says a class resolves to is what the compiler will do with it. No build needs it.
Install it anyway: one class of mistake is reported **only** here. `text-*` on a `frame`, `image-*` on a label,
`placeholder-*` outside a `textbox` — the transform pipeline never checks any of it, so those
compile clean and write the wrong property onto the wrong instance.

In VS Code, install **Vela LSP**, id `astra-void.vela-rbxts-lsp`, publisher `astra-void`:

```bash title="VS Code"
code --install-extension astra-void.vela-rbxts-lsp
```

It needs VS Code `^1.91.0`, and that is the whole install — the marketplace serves a per-platform
VSIX with the server binary inside it, so there is no npm package to add and nothing to configure
per project. The extension activates on TypeScript and TSX documents: open a `.tsx` file and the
server starts.

<Details title="How your theme reaches the server">
The extension watches `vela.config.{ts,json}`, evaluates every match, and pushes the result over the
wire — the server never reads the file itself. The `.ts` form is evaluated through **your project's**
`typescript`, so the pin at the top of this page decides whether your editor resolves custom theme
keys, not just whether your build runs.
</Details>

<Details title="Any other editor">
The server speaks LSP over stdio and has no VS Code dependency. Add it to the project:

<PackageInstall dev packageName="@vela-rbxts/lsp" />

Then point your client's server command at it:

```bash title="Server command"
npx --package @vela-rbxts/lsp vela-rbxts-lsp
```

`--package` is not optional here. The binary is named `vela-rbxts-lsp`, but the package that owns it
is `@vela-rbxts/lsp` — `vela-rbxts-lsp` on its own is the VS Code extension id, published as a VSIX
and not to npm, so a bare `npx vela-rbxts-lsp` resolves nothing. The platform binary itself arrives
as an optional dependency picked by `os`/`cpu`; there is nothing to select by hand. Two platforms
have no prebuilt binary on either channel — linux arm64 musl and Windows on ARM — and there the
server has to be built from source.

**Nothing hands the server your config here.** It has no config loader and no discovery of its own;
passing the resolved theme is the client's job, through `initializationOptions`. Skip it and the
server falls back to the built-in default theme, so every custom color and spacing key you defined
reports `unknown-theme-key` — against classes that build perfectly well, with nothing pointing at the
config as the cause.

[Editor setup](/vela-rbxts/guides/editor-setup/) has the payload shape, the method that updates it
after startup, and the full list of what the server does and does not implement.
</Details>

## Build and serve

On track A there is no Vela-specific build step — compile with roblox-ts as usual:

```bash title="Build — track A"
npx rbxtsc
```

On track B, lower first. `vela build` exits non-zero when a file fails to compile, so `&&` is the right joint:

```bash title="Build — track B"
npx vela build && npx rbxtsc
```

Either way, sync `out/` into Studio with Rojo the same way you already do:

```bash title="Serve"
rojo serve
```

You need no Vela-specific Rojo mapping.

<Details title="Why the runtime import resolves with no project change">
Most of what Vela produces is an ordinary Roblox property or a helper instance emitted as a JSX child,
and the rest is an import of `@rbxts/vela-runtime` — one ModuleScript the whole place shares, however
many files reach it.

That import resolves because of where the package sits. roblox-ts only resolves a package whose scope
directory is one of the project's `typeRoots`, and `node_modules/@rbxts` is the one every roblox-ts
project already lists and every Rojo template already maps to `ReplicatedStorage` — the same route
`@rbxts/react` takes. The runtime is published under that scope on purpose. (This is the mapping the
`nodeLinker` note above is about: the directory has to be real for either tool to walk into it.)

So the things that must exist in your place tree are the runtime host, `@rbxts/services`, and your UI
library — all of which your existing `node_modules` mapping already covers.
</Details>

## Check that it actually took

Two of the three ways this setup can fail are silent, so spend one build proving it worked. Put a
deliberately broken class on any `.tsx` element:

```tsx title="src/client/Smoke.tsx"
<frame className="bg-nope-500 p-4" />
```

Build, and read the output. You are looking for a warning naming `nope-500` — track A routes it
through roblox-ts's numbered diagnostics, track B prints it itself:

```text title="Track A — rbxtsc output"
src/client/Smoke.tsx:4:28 - warning TS89000: [@vela-rbxts/compiler] unknown-theme-key: Unknown theme key "nope-500" for background color utility in className literal.

4   return <frame className="bg-nope-500 p-4" />;
                            ~~~~~~~~~~~
```

```text title="Track B — vela build output"
client/Smoke.tsx:4:28 - warning vela/compiler(unknown-theme-key): Unknown theme key "nope-500" for background color utility in className literal.
```

If you get the warning, everything is wired: Vela is running and diagnostics are reaching you. Delete
the file.

<Details title="No warning — what to check">
**`className` is also a type error in your editor.** The ambient declaration is not loading — check
the `.d.ts` file exists inside `src` and is not named `src/vela-rbxts.d.ts`.

**`className` type-checks fine.** On track A, either the transformer is not running (check the
`plugins` entry spells the `/transformer` subpath, and that the file ends in `.tsx`), or your
roblox-ts version does not expose `context.addDiagnostic` and is discarding every Vela warning. That
second case is the dangerous one — it makes broken classes look clean forever — so upgrade roblox-ts
rather than living with it. On track B, check that you actually ran `vela build`, and that its header
names the directory you expected: `vela build: src -> .vela/src`.
</Details>

<Details title="What the emitted file should look like">
Check the emitted file — `out/` on track A, `.vela/src` on track B. `p-4` should have become a
`<uipadding>` child and the `className` attribute should be gone entirely; if the attribute survived
verbatim, the element was skipped.

The padding values will read as `__VelaRem.scale(new UDim(0, 16), 0)` rather than a bare
`new UDim(0, 16)`, and the file will have grown an import of `@rbxts/vela-runtime` at the top. That is
[rem](/vela-rbxts/guides/theming/#rem) doing its job: `16` is the value at the base viewport, and the
scaler is what follows the real one.
</Details>
