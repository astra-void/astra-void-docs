Vela borrows Tailwind's syntax, not its scope. Roblox UI has a different layout model, a different
set of primitives, and no CSS box model, so a faithful port would produce a large surface of classes
that cannot mean anything. What Vela ships instead is a Roblox-oriented mapping: the utilities that
correspond to real Roblox properties and helper instances, a few structural emulations where the
correspondence can be built honestly — margins become a wrapper frame, `divide-*` becomes separator
frames — and loud rejection of everything that cannot be expressed at all. This page is the honest
map of where the edges are at **0.4.0**.

## What is in scope

Utilities apply to exactly eight host elements:

`frame`, `scrollingframe`, `canvasgroup`, `textlabel`, `textbutton`, `textbox`, `imagelabel`, `imagebutton`

They also apply to **components** — any tag starting with an uppercase letter, or any member
expression such as `<Switch.Root />`. A `className` there is lowered into props and helper children
on the component itself, which only reaches the screen if the component forwards the props and
children it does not consume down to a host element. See
[How it works](/vela-rbxts/getting-started/how-it-works/#classname-on-components).

Anything that is neither is skipped, keeps its `className` verbatim, and reports
`classname-on-unsupported-host` — lowercase intrinsics Vela does not implement, such as `screengui`,
and namespaced tags such as `<svg:rect />`, which never count as components.

Within those eight, the covered ground at 0.4.0 is wide: colors (including arbitrary hex and `/N`
opacity modifiers), gradients, borders, rings and outlines, corner radius, shadows, padding,
margins, gap and `space-*`, `divide-*` separators, sizing and min/max constraints, position on all
four edges, anchor point, translation, z-index, layout order, rotation, scale, opacity, aspect
ratio, flex layout and flex items, grid, typography from size and weight through line height, case
transforms and decorations, visibility, overflow, image scaling, interactivity, overscroll, and a
`TweenService`-backed motion layer with nine runtime variants including `hover:`. The
[utilities reference](/vela-rbxts/reference/utilities/) enumerates all of it with the exact accepted
values.

## What is permanently out

Vela distinguishes a class it has never heard of (`unsupported-utility-family` — the typo bucket)
from a real Tailwind family that Roblox UI cannot express (`no-roblox-equivalent`). The second list
is a design decision, not a roadmap: letter spacing (`tracking-*`), per-element filters (`blur-*`,
`backdrop-*`, `grayscale`), 3D transforms (`skew-*`, `perspective-*`), the CSS positioning model
(`absolute`, `fixed`, `sticky`), grid spans (`col-span-*`), cursors, text indentation, and the rest
of the [not-implemented table](/vela-rbxts/reference/utilities/#not-implemented). Each entry names
what Roblox is missing, so a warning there is an answer rather than a dead end.

## The gaps that do not announce themselves

Most of Vela's edges produce a diagnostic. The ones below do not, and they are worth reading twice.

<Callout title="Four silent gaps">
**Host-element restrictions are editor-only.** Vela knows which utilities make sense on which tag —
text utilities on `textlabel`/`textbutton`/`textbox`, `image-*` and `object-*` on image elements,
`placeholder-*` on `textbox`, `overscroll-*` on `scrollingframe`. That table drives completions,
hover, and the `unsupported-host-utility` diagnostic in the language server. **The transform
pipeline never consults it.** So `<frame className="text-red-500" />` compiles clean, emits
`TextColor3` on a Frame, and produces no compile-time warning at all. Install the
[editor tooling](/vela-rbxts/guides/editor-setup/) if you want this caught.

**Components that drop what they are handed.** Vela emits the resolved props on the component and
prepends helper instances as its children; if the component does not forward its unrecognized props
to a host element and render `children`, all of it vanishes. Nothing warns you, in the editor or in
the build.

**The runtime subset.** When a `className` is a dynamic expression, the in-game resolver handles
colors, backgrounds, radius, padding, margins, gap, sizing, `divide-*`, case transforms,
decorations, and motion — and **silently drops everything else**. Layout, alignment, text size and
color, position, and constraints all vanish with no warning of any kind. A `flex-col` that works in
a string literal disappears when you move it into a ternary.
[Dynamic class names](/vela-rbxts/guides/dynamic-class-names/) covers the whole divergence.

**Gradient stops set to `transparent`.** `from-transparent`, `via-transparent`, and `to-transparent`
produce no diagnostic — the stop is silently dropped, and a two-stop gradient quietly renders as a
flat fill. Every other family without a transparency channel (`placeholder-*`, `divide-*`) does
warn.
</Callout>

## Known bug in the released 0.4.0

<Callout title="Breakpoints and orientation do not work in 0.4.0">
The runtime helper in the published `0.4.0` reads `Camera.ViewportSize` **once, when the element
mounts** — and at mount Roblox often still reports a 1×1 viewport. The result is worse than "resizes
are not tracked": every width test sees width 1, so **`sm:`, `md:`, and `lg:` rules never match, and
orientation is evaluated as landscape**, until something replaces the camera. A fix that follows the
viewport signal and reacts to resizes is merged upstream and pending release as a compiler patch.

Until that ships, treat the input variants (`touch:`, `mouse:`, `gamepad:`) and `hover:` as the
reliable ones — their signals are subscribed correctly — and drive breakpoint-style reflow from your
own state: read `ViewportSize` yourself, connect to its change signal, and branch between two static
class strings as shown in [Dynamic class names](/vela-rbxts/guides/dynamic-class-names/).
</Callout>

Two smaller sharp edges, both documented where they live: `gap-*` on a `grid` element currently
emits a conflicting `UIListLayout` alongside the `UIGridLayout` it feeds
([utilities reference](/vela-rbxts/reference/utilities/#grid)), and `divide-*` separators interact
poorly with explicit `LayoutOrder` and double-count the parent's `gap-*`
([utilities reference](/vela-rbxts/reference/utilities/#divide)).

## Release state

Every package in the repo is at **0.4.0**, versioned in lockstep: `vela-rbxts` itself and the
`@vela-rbxts/*` scope covering the compiler, config, core, IR, types, host adapter and language
server, plus the `vela-rbxts-lsp` VS Code extension. There is no independent versioning, so a fix
anywhere moves everything. Releases are tagged from `v0.3.0` onward, and a pending changeset holds
the viewport fix described above plus a `divide-*` separator-placement fix.

Two consequences follow from the version being what it is. First, nothing is enforced at install
time: no package declares `peerDependencies`, and the only `engines` field anywhere is the VS Code
extension's `vscode: ^1.90.0`, so a mismatched roblox-ts or TypeScript will fail at build rather
than at install. Second, prebuilt native binaries do not cover every platform — notably there is no
`aarch64-pc-windows-msvc` target, so Windows on ARM is not supported, and no linux arm64 musl build.

## A performance note

Config discovery re-reads, re-transpiles and re-executes `vela.config.ts` for **every eligible
source file**. There is no caching layer between files. On a project with hundreds of `.tsx` files
this is hundreds of `transpileModule` calls per build. Keeping `vela.config.ts` to a plain
`defineConfig` call with literal values — no imports beyond `vela-rbxts`, no computed theme
generation, no side effects — keeps that cost small and predictable. (A JSON config,
`vela.config.json`, skips the transpile step but is still re-read per file.)
