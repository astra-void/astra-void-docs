The fastest way to understand Vela is to write a small component and read what comes out the other side. This page builds a panel with a title and a caption, then walks through what each class name became.

<VelaPreview
  height={200}
  label="The panel this page builds, compiled by Vela and rendered in the browser."
  scene="PanelScene"
/>

That preview is not a screenshot and not a mock-up: the example was lowered by the same compiler `rbxtsc` loads, and the emitted Roblox tree is what you see. The **Classes** tab is the source with `className` on it, the **Lowered** tab is what came out — and that source is the snippet below, line for line, so what you copy from this page is what the preview renders.

Open the **Lowered** tab and you will also find `BackgroundTransparency` and `BorderSizePixel` on elements whose classes never mention either. That is [preflight](/vela-rbxts/reference/config/#preflight): Roblox paints every `GuiObject` as an opaque gray box, so any element carrying a `className` starts from transparent-and-borderless unless something actually paints it.

## The component

```tsx title="src/client/Panel.tsx"
import React from "@rbxts/react";

export function Panel() {
  return (
    <frame className="flex flex-col gap-4 p-4 rounded-lg bg-slate-800 border border-slate-700 w-80 h-24">
      <textlabel
        className="w-full h-6 text-left text-slate-100 text-lg font-semibold"
        Text="Loadout"
      />
      <textlabel
        className="w-full h-5 text-left text-slate-400 text-sm"
        Text="Two slots remaining"
      />
    </frame>
  );
}
```

Every class here resolves at compile time — nothing in this file reads the theme at runtime. The one thing that does survive into the output is the rem scaler, which is what makes those offsets follow the player's viewport; [What comes out](#what-comes-out) shows it.

<Callout title="Why every element carries a size">
`h-24` on the panel and `w-full h-6` on the labels are not Vela requirements — they are Roblox
defaults showing through. A `GuiObject` starts at `Size = (0, 0, 0, 0)`, and a class list that only
sets a width leaves the height axis at zero, so the instance is real, correct, and zero pixels tall.
Drop those classes and this panel compiles cleanly to an invisible frame containing two invisible
labels. `w-fit`/`h-fit` lower to `AutomaticSize` if you would rather Roblox measure the content.
</Callout>

## Put it on screen

A component that is never mounted renders nothing, and Vela changes nothing about how you mount one
— this is ordinary `@rbxts/react-roblox`. The one Vela-specific detail is the wrapper: `screengui`
is **not** one of the eight host elements Vela lowers, so classes belong on a `frame` inside it, not
on the `screengui` itself.

```tsx title="src/client/main.client.tsx"
import React from "@rbxts/react";
import { createPortal, createRoot } from "@rbxts/react-roblox";
import { Players } from "@rbxts/services";
import { Panel } from "./Panel";

const playerGui = Players.LocalPlayer.WaitForChild("PlayerGui");
const root = createRoot(new Instance("Folder"));

root.render(
  createPortal(
    <screengui ResetOnSpawn={false} ZIndexBehavior={Enum.ZIndexBehavior.Sibling}>
      <Panel />
    </screengui>,
    playerGui,
  ),
);
```

Rojo maps this file into `StarterPlayer/StarterPlayerScripts` the same way it would any other client
entry point; the `.client` in the filename is what makes roblox-ts emit a LocalScript. Note the
extension too — Vela only ever transforms `.tsx` files, so a `className` assembled in a `.ts` helper
is invisible to it.

Build, sync, and press play: the panel from the preview above is now in your place.

## What each class lowers to

The `frame` classes split into two kinds of result: properties set directly on the Frame, and helper instances that have to exist as children because Roblox models layout, padding, corners and strokes as separate objects.

| Class | Result | Value |
|---|---|---|
| `flex` | `UIListLayout` child, `FillDirection` | `Enum.FillDirection.Horizontal` |
| `flex-col` | `UIListLayout.FillDirection` | `Enum.FillDirection.Vertical` |
| `gap-4` | `UIListLayout.Padding` | `new UDim(0, 16)` |
| `p-4` | `UIPadding` child, all four sides | `new UDim(0, 16)` |
| `rounded-lg` | `UICorner.CornerRadius` | `new UDim(0, 8)` |
| `bg-slate-800` | `BackgroundColor3` | `Color3.fromRGB(29, 41, 61)` |
| `border` | `UIStroke.Thickness` | `1` |
| `border-slate-700` | `UIStroke.Color` and `Transparency` | `Color3.fromRGB(49, 65, 88)`, `0` |
| `w-80 h-24` | `Size` | `UDim2.fromOffset(320, 96)` |

Every offset in that column is a **rem** value written at the base viewport, not a fixed pixel count:
`new UDim(0, 16)` is what `p-4` is worth at 1920×1020, and it scales from there. See
[rem](/vela-rbxts/guides/theming/#rem).

A few of those deserve a note.

`flex` and `flex-col` write to the same instance. Bare `flex` sets `FillDirection` to `Horizontal`; `flex-col` then overwrites it with `Vertical`. Only one `UIListLayout` is emitted, no matter how many layout classes you stack on the element. If you only ever want a column, `flex-col` alone is enough.

`gap-4` and `p-4` both resolve `4` through the theme's `spacing` scale, which is where the built-in default has its only entry: `"4": "new UDim(0, 16)"`. Every other numeric spacing key — `p-2`, `gap-6`, `p-1.5` — comes from an arithmetic fallback instead: the key must parse as a non-negative multiple of `0.5`, and the result is that number times four pixels. That is why `w-80` is 320 pixels rather than a lookup failure.

`w-80` and `h-24` merge into one `Size` rather than one replacing the other, which is why the two of them produce a single `UDim2.fromOffset(320, 96)`. Drop the `h-24` and the height axis falls back to zero — `UDim2.fromOffset(320, 0)` — and the panel disappears. (On the runtime path that merge does not happen; the later token wins. See [dynamic class names](/vela-rbxts/guides/dynamic-class-names/).)

`border` and `border-slate-700` are two different utilities that happen to share a prefix. The bare form sets thickness; the color form sets color and transparency. Writing only `border-slate-700` gives you a colored stroke with no explicit thickness set.

The `textlabel` classes are mostly text-only utilities: `text-slate-100` and `text-slate-400` set `TextColor3`, `text-lg` sets `TextSize` to `18`, `text-sm` sets it to `14`, `text-left` sets `TextXAlignment` to `Left`, and `font-semibold` sets `FontFace` to `new Font("rbxasset://fonts/families/SourceSansPro.json", Enum.FontWeight.SemiBold)`. Their `w-full h-6` and `w-full h-5` go through the same sizing path as the panel's, mixing a scale and an offset — `new UDim2(1, 0, 0, 24)`.

Note that `text-*` is disambiguated by value, not by prefix: a known size key becomes `TextSize`, an alignment keyword becomes `TextXAlignment`, and anything else is treated as a color. There is no such thing as an unrecognised `text-*` class — misspell a size and you get a theme-key warning about a color.

## What comes out

The transformer removes `className` entirely, emits the resolved properties on the element, and prepends the helper instances as children ahead of whatever children you wrote. This is the actual emitted TSX, with line breaks added:

```tsx title="Transformed output (line breaks added; nothing else changed)"
import { createVelaRemScaler, __VelaOpacity } from "@rbxts/vela-runtime";
const __VelaRem = createVelaRemScaler({
  base: 16, min: 8, max: 64, baseResolution: { x: 1920, y: 1020 },
});

<frame
  BackgroundColor3={Color3.fromRGB(29, 41, 61)}
  Size={__VelaRem.scale(UDim2.fromOffset(320, 96), 11)}
  BorderSizePixel={0}
>
  <uilistlayout
    FillDirection={Enum.FillDirection.Vertical}
    Padding={__VelaRem.scale(new UDim(0, 16), 4)}
    SortOrder={Enum.SortOrder.LayoutOrder}
  />
  <uipadding
    PaddingTop={__VelaRem.scale(new UDim(0, 16), 5)}
    PaddingRight={__VelaRem.scale(new UDim(0, 16), 6)}
    PaddingBottom={__VelaRem.scale(new UDim(0, 16), 7)}
    PaddingLeft={__VelaRem.scale(new UDim(0, 16), 8)}
  />
  <uicorner CornerRadius={__VelaRem.scale(new UDim(0, 8), 9)} />
  <uistroke Thickness={__VelaRem.scale(1, 10)} Color={Color3.fromRGB(49, 65, 88)} Transparency={0} />
  <textlabel
    Text="Loadout"
    TextXAlignment={Enum.TextXAlignment.Left}
    TextColor3={Color3.fromRGB(241, 245, 249)}
    TextSize={__VelaRem.scaleText(18, 0)}
    Size={__VelaRem.scale(new UDim2(1, 0, 0, 24), 1)}
    FontFace={new Font("rbxasset://fonts/families/SourceSansPro.json", Enum.FontWeight.SemiBold)}
    BorderSizePixel={0}
    BackgroundTransparency={1}
  />
  <textlabel
    Text="Two slots remaining"
    TextXAlignment={Enum.TextXAlignment.Left}
    TextColor3={Color3.fromRGB(144, 161, 185)}
    TextSize={__VelaRem.scaleText(14, 2)}
    Size={__VelaRem.scale(new UDim2(1, 0, 0, 20), 3)}
    BorderSizePixel={0}
    BackgroundTransparency={1}
  />
</frame>
```

Four things in there were never in your class list. `BorderSizePixel` and the labels' `BackgroundTransparency` are [preflight](/vela-rbxts/reference/config/#preflight), as described above — the panel does not get the transparency because `bg-slate-800` paints it. `SortOrder = LayoutOrder` is emitted on every Vela layout so that `order-*` works at all.

And every offset is wrapped in `__VelaRem.scale`. That is [rem](/vela-rbxts/guides/theming/#rem): the literal inside is the value at a 1920×1020 viewport, and the scaler is what follows the real one, so `p-4` reads the same on a phone and on a 4K monitor. The trailing number is a slot, so the file allocates one binding per scaled offset rather than one per render; `TextSize` goes through `scaleText`, which additionally caps at 100. Pin `theme.rem` and the wrappers disappear from the emit entirely, leaving the plain literals.

That is why the **Lowered** tab above shows those plain literals and this block does not: a preview frame is a few hundred pixels wide, so every preview in these docs is compiled with rem pinned to keep the render one pixel per pixel. What you see here is the default emit — what your project gets.

One more thing the compiler adds that is not shown above: a component definition's root is wrapped in `<__VelaOpacity.Fade>`, which is how an `opacity-*` written on an ancestor reaches a subtree that was lowered at compile time. It renders no instance, so the Roblox tree keeps its shape.

Because the helpers are prepended, they always sort ahead of your own children in the emitted JSX. That does not affect layout — `UIListLayout` ignores non-`GuiObject` siblings — but it is worth knowing if you index children positionally.

This is the **static path**, and it is the one you want. The element keeps its original tag, no class list is parsed in game, and every token was resolved and checked at build time. The [pipeline page](/vela-rbxts/getting-started/how-it-works/) explains when that stops being true.

## Something that does not work

Vela is a Roblox-shaped subset of Tailwind, not a port of it. Letter spacing is a good example — the Roblox text engine exposes no such property, so `tracking-*` cannot mean anything:

```tsx title="This warns"
<frame className="tracking-wide p-4 bg-slate-800" />
```

The build still succeeds, but the transformer reports a warning through roblox-ts:

```text title="Compiler output"
[@vela-rbxts/compiler] no-roblox-equivalent: Tailwind "tracking" utilities have no Roblox equivalent, so "tracking-wide" is ignored.
```

`p-4` and `bg-slate-800` are applied normally; only the inexpressible token is dropped. A class Vela has never heard of — a typo, say — gets `unsupported-utility-family` instead, so the two failure modes are distinguishable in the build log.

Colors have their own failure mode. A palette in the theme is a set of shades, and you reach a shade either by naming it or through the palette's `DEFAULT`. A palette that has neither is an error rather than a fallback — say your config adds a `brand` family with only `500` and `700`:

```tsx title="This warns too"
<frame className="bg-brand" />
```

```text title="Compiler output"
[@vela-rbxts/compiler] color-missing-shade: Color palette "brand" for background color utility has no "DEFAULT" shade, so it requires an explicit shade such as "brand-500" in className literal.
```

Write `bg-brand-500`, or add a `DEFAULT` key to the palette so the bare form resolves. The built-in palettes all ship a `DEFAULT` mirroring their `500`, which is why `bg-slate` needs no shade while `bg-brand` does.

<Callout title="Where the squiggle lands">
For a static string `className` like both of these, the compiler anchors each diagnostic to the offending token's real position, so the underline lands on the class you actually wrote. That is not true everywhere. A computed `className` produces diagnostics with no range, and the host adapter falls back to searching for the first textual occurrence of the token anywhere in the file, so the underline can land on an earlier comment or string. Diagnostics that carry no token at all — a parse failure, an emit failure, or a crash inside the compiler — get no search either and are reported at the very start of the file. The message and code are always correct.
</Callout>

The full list of codes, and what each one means, is in the [diagnostics reference](/vela-rbxts/reference/diagnostics/).
