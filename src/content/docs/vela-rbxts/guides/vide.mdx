Vela emits for [Vide](https://centau.github.io/vide/) as well as React, from **0.12.0**, and
everything this documentation says about utilities, variants, the theme and the two lowering paths
says the same thing under either target.

**A Vide project needs no Vela config for this.** With `framework` unset — which includes having no
`vela.config.ts` at all — Vela reads the target off your `tsconfig.json`, and the setting it reads is
the one a Vide project already has so that roblox-ts compiles its JSX:

```json title="tsconfig.json — enough on its own"
{
  "compilerOptions": {
    "jsx": "react",
    "jsxFactory": "Vide.jsx",
    "jsxFragmentFactory": "Vide.Fragment"
  }
}
```

There is nothing else to install either. Both runtime hosts ship with `vela-rbxts`, and the one you do
not emit for is an inert ModuleScript no module imports — see [installation](/vela-rbxts/getting-started/installation/#install-the-packages).

<Callout title="Be on 0.12.1 or later if you have a config file at all">
On 0.12.0 the inference ran only for a project with **no** `vela.config.ts` whatsoever, so a Vide
project whose config set a theme or a plugin compiled against the React host and emitted an import of
`@rbxts/vela-runtime` — a package it has no reason to have installed. Fixed in
[0.12.1](/vela-rbxts/reference/release-notes/#0121). On 0.12.0, name `framework: "vide"` explicitly.
</Callout>

The config key exists for the cases where you want to say it out loud rather than have it read — see
[naming the target explicitly](#naming-the-target-explicitly) at the end of this page.

## The static path is the same output

A statically lowered element is *identical* source under both targets, because there is nothing
framework-shaped in it. Vide's JSX intrinsics are the same lowercase Roblox class names React's are,
and its props are Roblox instance properties directly:

```tsx title="Both targets emit this"
<frame BackgroundColor3={Color3.fromRGB(49, 65, 88)} Size={__VelaRem.scale(UDim2.fromOffset(160, 0), 4)}>
  <uipadding PaddingTop={__VelaRem.scale(new UDim(0, 16), 0)} />
</frame>
```

The whole token → utility pipeline is shared: the same parser, the same theme, the same diagnostics,
the same helper children, the same [rem](/vela-rbxts/guides/theming/#rem) scaling. What differs is the
module specifier at the top of the file — `@rbxts/vela-runtime-vide` rather than `@rbxts/vela-runtime`,
so React never reaches a Vide place — and what happens on the runtime path.

## A dynamic class value has to be a thunk

This is the one thing you write differently. A Vide component body runs **once**; there is no
re-render to refresh a plain value with. So a class value that changes has to be written as a function,
the way any other derived Vide prop is:

```tsx title="src/client/Button.tsx"
const active = source(false);

// Tracked — the class list is re-read whenever `active` changes.
<textbutton className={() => (active() ? "bg-blue-600" : "bg-slate-700")} />

// Not tracked — read once, at the moment the component body ran.
<textbutton className={active() ? "bg-blue-600" : "bg-slate-700"} />
```

`className` is typed to allow both (`ClassValue | (() => ClassValue)`), and the second line is not an
error — it is a class list that was correct once. Nothing warns about it, for the same reason Vide
does not warn about any other prop read outside a thunk.

The editor reads inside the thunk since **0.12.2** — completions, hover, swatches, diagnostics and the
class sort all work on a deferred class value the way they do on a literal one. See
[editor setup](/vela-rbxts/guides/editor-setup/#what-the-language-server-provides).

<Callout title="A branch still resolves at compile time either way">
A thunk is about *tracking*, not about lowering. `() => (active() ? "bg-blue-600" : "bg-slate-700")` names
both tokens in the source, so both are resolved by the compiler with the full utility set and the element
is handed the resolved props alongside the test — exactly as the React form is. The only difference in the
emit is that the test itself is thunked, so reading it tracks. See
[dynamic class names](/vela-rbxts/guides/dynamic-class-names/#a-branch-lowers-at-compile-time).
</Callout>

That is worth seeing whole, because it is most of what "the same output" means. Both targets resolve the
branch into the same two `__velaRules`; what differs is the one line inside `__velaTests` — and the
runtime the host is imported from.

## What the runtime host does differently

Nothing you have to think about, on a host element. The Vide host binds an effect that writes whatever
the current resolution names, which is what a re-render is for React: a property that appears is
written, one that disappears goes back to what the element declared, or to the class default where it
declared nothing. Interaction variants, `transition-*` and `animate-*`, the text transforms, `divide-*`
separators and the `opacity-*` model all behave as the React host's do — they run on the same
target-neutral core.

The reactive seams underneath are different, and two of their consequences reach you.

### A component element's props are fixed at the call

Vide hands a component its props once, rather than writing to an instance it owns. So on a **component**
element, which props the host can pass down is decided when the component is called:

```tsx title="A prop that only a later reading names cannot appear"
<Card className={() => (loud() ? "bg-red-500 rounded-xl" : "bg-slate-700")} />
```

Both branches are read up front here, so both `BackgroundColor3` and the `UICorner` are accounted for.
What cannot work is a name that no reading at call time produced — a class value arriving from an opaque
call that later yields a family nothing anticipated. A host element has no such limit: it is an instance
the host owns, and it writes whatever the resolution now names.

### A late `m-*` cannot be honoured

A margin is a wrapper instance *above* the element, and Vide parents an element as soon as it builds
one — so a margin box cannot be introduced afterwards. The compiler closes almost all of this by saying
so up front: a class value naming `m-*` anywhere this pass can see, in a static token or in a branch,
emits `__velaMarginBox` and the host builds the box **before** the element.

React emits nothing in that position at all, because the render that resolves a margin also renders the
wrapper around it — the hint would be a prop with no reader.

What is left is a margin named where nothing can read it, arriving out of an opaque call. The runtime
**warns** there rather than rendering the element unspaced, so it is a message in the output rather
than a layout you have to reverse-engineer.

## Naming the target explicitly

The inference is a walk, and it is worth knowing how far it reaches before you decide you need to
override it: from each source file's directory upward to the nearest `tsconfig.json`, following a
**relative** `extends` up to eight levels, reading `compilerOptions.jsxFactory`. A factory beginning
with `Vide.` selects Vide; anything else, or none found, leaves the default of React.

Naming the key in `vela.config.ts` always wins, and it wins by being **present** rather than by its
value:

```ts title="vela.config.ts — only if you want to override the walk"
import { defineConfig } from "vela-rbxts";

export default defineConfig({ framework: "vide" });
```

So `framework: "react"` pins React even under a Vide `jsxFactory`, and `framework: "vide"` pins Vide
where the walk would not have found the factory — a tsconfig reached through a non-relative `extends`,
or one nested deeper than the walk goes. Both are escape hatches; a project whose tsconfig says `Vide.`
in the ordinary way has no reason to write either.

<Callout title="One target per project, not per file">
`jsxFactory` is a program-wide TypeScript setting, so a project pointing it at Vide cannot compile React
JSX at all. The choice is per project by construction, and this is also why an unset `framework` is read
as *the default* rather than as a positive request for React — a project that never mentioned Vela's
config but compiles Vide JSX is asking for Vide.
</Callout>

## Writing the declaration file

Unchanged. The same side-effect import augments both namespaces — `React.Attributes` and
`Vide.Attributes` — so one file covers whichever you compile for:

```ts title="src/vela-env.d.ts"
import "vela-rbxts";
```
