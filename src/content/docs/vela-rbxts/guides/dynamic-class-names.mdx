`className` is typed as `ClassValue`, so you can compute it: template strings, ternaries, arrays, values from props or state. The type system will not stop you, and neither will the compiler.

What changes is *how* the class string is lowered. When Vela can collapse the expression to a fixed set of tokens at compile time, it takes the **static path** and lowers straight to props. When it cannot, the element falls onto the **runtime path**, where a resolver inlined into your game does the same work while the game is running.

Until 0.8.0 those two paths supported very different utility sets, and the difference was silent. That is over — the question now is cost, not coverage.

## The two paths resolve the same utilities

As of **0.8.0** every utility family the [reference](/vela-rbxts/reference/utilities/) documents resolves on both paths, with the same semantics: opacity modifiers (`bg-blue-600/50`), arbitrary values (`w-[120px]`, `text-[13px]`), and the families that only meet at the end — the two `Size` axes, `Position` and `AnchorPoint`, `FontFace`, a grid track and the gap it gives back — all composed the way the static path composes them.

One asymmetry remains, and it favours the runtime path: **a utility the host element cannot carry is dropped rather than written.** Writing `TextColor3` onto a `Frame` is a hard Roblox error, so the runtime host checks the tag first. The static path does not — `<frame className="text-lg" />` emits `TextSize` on a `Frame` with no diagnostic and fails in game.

`opacity-*` is the one family where the paths deliberately hand off to each other. As of **0.10.0** the compiler stops fading the subtree under a computed `className` at compile time and leaves the whole class list to the host, which resolves it and hands its children one alpha — so a fade written inside a variant recipe reaches the subtree it is written over, exactly as a literal one would. See [`opacity-*`](/vela-rbxts/reference/utilities/#effects).

<Callout title="If you are on an older release, coverage is the problem">
The parity work landed over three releases, and on anything earlier a computed `className` loses
utilities **with no diagnostic at all** — no compile warning, no editor squiggle, no runtime error.

- **Before 0.6.0**, every `text-{color}` in a computed string was dropped, so labels kept Roblox's
  near-black default and went invisible on dark surfaces.
- **Before 0.7.0**, `flex-row`, `items-*`, `justify-*`, `w-fit`/`h-auto`/`size-fit`, `text-<size>`,
  `text-left|center|right` and `font-<weight>` were dropped. A computed `flex items-center gap-2`
  produced a `UIListLayout` at its default **vertical** fill direction, so the row rendered as an
  uncentered column.
- **Before 0.8.0**, positioning, the box constraints, the grid, gradients, `ring-*`/`outline-*`,
  shadows, `z-*`, `rotate-*`, `scale-*`, `opacity-*`, `order-*`, `leading-*`, `self-*`, `content-*`,
  `object-*`, `pointer-events-*`, `space-*`, `whitespace-*` and the ScrollingFrame families were
  dropped.

Upgrading is the fix. If you cannot, keep the affected element on the static path.
</Callout>

## What the runtime path still costs

Parity is not equivalence. Four things follow from resolving classes in-game rather than at build time, and none of them are going away.

**No diagnostics.** The compiler never sees the final string, so nothing checks it. A typo like `bg-blu-600` is a `unknown-theme-key` warning on the static path and complete silence on the runtime path — the token resolves to nothing and the element renders without a background. This is the single strongest reason to prefer a static class list.

**No editor support.** Completions, hover, and the color swatches all work from the literal text. A class name assembled at runtime is a string to the LSP, not a class list.

**The runtime helper is inlined into the module.** It is a substantial block of code, emitted once per module that needs it, and the element renders as `VelaRuntimeHost` rather than your tag. It no longer *costs* much in Luau's local-register budget — 0.9.0 folded it into a single initializer and 0.10.0 split that into thirteen namespaces, taking the busiest register file in an emitted file from 177 of the 200 Luau allows down to 65. Below 0.9.0 a large enough component could fail to compile because of it; see [troubleshooting](/vela-rbxts/guides/troubleshooting/#out-of-local-registers).

**Theme values are re-parsed from text.** This is the sharpest remaining edge. The static path splices your theme's roblox-ts expression into the output; the runtime path serializes the resolved config to JSON and re-parses it in Luau with two hand-written parsers that accept exactly `Color3.fromRGB(r, g, b)` and `new UDim(a, b)` with numeric arguments. A theme value that is valid roblox-ts but not in one of those shapes — `Color3.new(0.1, 0.2, 0.3)`, `Color3.fromHex(...)`, `new UDim(0, PADDING)` — compiles fine and then **silently degrades in game**: unparseable colors drop out of the runtime scale, unparseable radius and spacing values fall back to `new UDim(0, 0)`. See [configuration](/vela-rbxts/reference/config/#values-are-roblox-ts-expression-strings).

## What puts an element on the runtime path

Not just a computed `className`. Any of these is enough:

| Trigger | Note |
|---|---|
| A `className` expression that does not collapse | Including a ternary between two string *literals* |
| Any variant prefix | `sm:`, `touch:`, `hover:`, `active:`, `focus:`, `dark:` — even in a plain literal |
| The structural utilities | Margins, `divide-*`, `animate-*` build wrappers and separators no static prop can express |

Variant-prefixed tokens are analyzed statically and serialized as **rules**, so they were never subject to the old coverage gap — it was the dynamic `className` case specifically that narrowed.

<Callout title="A ternary between two literals is not folded">
`className={on ? "bg-blue-600" : "bg-zinc-800"}` looks like something the compiler could collapse to
two static branches, and it does not: the element goes to the runtime path. The only way to keep both
branches static is to branch the whole JSX element.

An **array** of literals *is* collapsed — `className={["flex", "gap-2"]}` stays on the static path.
</Callout>

## How to tell which path an element took

There is no diagnostic and no flag, so check the emitted roblox-ts. A static-path element keeps its original tag and gains plain props plus helper children. A runtime-path element is rendered as `VelaRuntimeHost` and carries `__velaTag` and, when variants are involved, `__velaRules`. If you see `VelaRuntimeHost` on an element you expected to be static, something in its `className` did not collapse.

## Staying static when it matters

Coverage no longer forces the choice, so the rule is softer than it used to be: reach for a static class list where losing compile-time checking would hurt, and compute freely elsewhere.

### Branch the element, not the string

Instead of computing one string, choose between two complete literals. Each branch is a static string, so each takes the static path with full diagnostics and no runtime helper:

```tsx title="src/client/Card.tsx"
import React from "@rbxts/react";

interface CardProps {
  emphasized: boolean;
}

export function Card({ emphasized, children }: CardProps & { children?: React.Element }) {
  return emphasized ? (
    <frame className="flex flex-col items-center gap-2 p-4 rounded-lg bg-slate-700">
      {children}
    </frame>
  ) : (
    <frame className="flex flex-col items-center gap-2 p-4 rounded-lg bg-slate-800">
      {children}
    </frame>
  );
}
```

The duplication is real. That is the trade: two literals that both compile to plain props and are both checked, versus one computed string that is checked by nothing. When the shared part grows large enough to be a maintenance problem, push the shared layout onto a static wrapper and let only the varying element branch.

### Or use a variant instead of computing

If the thing driving the class is something Vela can observe — pointer, press, focus, viewport, input device, color scheme — a variant expresses it without any computation, and variants keep the full utility set:

```tsx title="No computed string needed"
<textbutton className="bg-slate-800 hover:bg-slate-700 active:bg-slate-600 transition" Text="Play" />
```

### Computing is fine for the rest

A computed `className` for state your app owns is a normal thing to write, and at 0.11.0 it does what it says:

```tsx title="Fine — resolves fully, just without compile-time checking"
const tone = disabled ? "bg-slate-800 text-slate-500" : "bg-blue-600 text-white";
return <frame className={`flex items-center gap-2 p-2 rounded-md ${tone}`} />;
```

Every token here resolves, including the `flex items-center` that would have been dropped before 0.7.0. What you give up is the typo check.

## Components take the same two paths

Everything on this page applies to `className` on your own components too — `<Panel className={classes} />` is lowered exactly like `<frame className={classes} />`.

The one visible difference is the tag. On the runtime path the component is swapped for `VelaRuntimeHost` as usual, but `__velaTag` carries a live reference rather than a string: `__velaTag={Panel}`, or `__velaTag={Switch.Root}` for a member expression. The helper then renders your component with the resolved props and the helper children.

Which means the component has to forward what it does not consume, or none of it lands. That is the trap worth internalizing before you reach for a computed `className` on a component — it is described in full in [How it works](/vela-rbxts/getting-started/how-it-works/#classname-on-components), and there is no diagnostic for getting it wrong.

Note also that a component only emits the modifier-sibling shape — `<Switch.Root …><uicorner /><textbutton /></Switch.Root>` — on the **static** path. Go dynamic and the `UICorner` is built at runtime instead, so an element that exists to demonstrate that emit needs to stay static.
